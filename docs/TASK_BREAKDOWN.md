# План реализации Militantyx

Статусы: [ ] — не выполнено; [-] — начато; [x] — артефакт уже есть в репозитории.
Отметка наличия не заменяет повторной проверки на целевой среде.
Каждый пункт ниже — отдельная задача с проверяемым результатом.

## Исходное состояние

- [x] Созданы C++23/CMake-проект, монорепозиторий и модуль logging.
- [x] Есть форматирование, проверки, logger smoke test и подключение Catch2.
- [x] Подготовлены Dockerfile и Compose-каркас с ClickHouse.
- [-] PCAP-модуль: заголовки и реализация пустые, Catch2-тест содержит REQUIRE(true).
- [ ] Подключить реальную capture-библиотеку к тесту после реализации.
- [ ] Согласовать Dockerfile с Catch2: CMake уже требует пакет, образ его пока не устанавливает.

## Этап 0. Контракты и проверяемые сценарии

Зависимости: отсутствуют. Этот этап предшествует детекторам и обучению.

- [ ] T01. Описать матрицу «сценарий → наблюдаемые признаки → ожидаемый результат».
  Включить TLS-beaconing, DoH/DoT и кандидатов OpenVPN/WireGuard; для каждого
  указать поддерживаемые версии, конфигурации и ограничения.
- [ ] T02. Создать манифест PCAP-наборов: источник, сценарий, метки, разрешённая
  политика, ожидаемые потоки и временные интервалы. Добавить легальный фон:
  браузер, обновления, мониторинг, AnyDesk и разрешённый VPN/DNS.
- [ ] T03. Описать точные контракты FlowRecord, WindowRecord, AnalysisJob,
  AnalysisResult, Alert и SensorHealth с JSON-примерами. Зафиксировать единицы,
  отсутствующие поля, идентификаторы, ревизии и накопительные счётчики.
- [ ] T04. Описать конфигурацию: защищаемые подсети, разрешённые резолверы/VPN,
  лимиты памяти, тайм-ауты, длина окон, бюджет DPI и размер очередей.
- [ ] T05. Определить протокол эксперимента: разбиение по сессиям/хостам/времени,
  метрики, оборудование и способ измерения задержек. Зафиксировать целевые
  бюджеты до итогового теста.

Готово: для каждой угрозы есть положительный и отрицательный сценарий,
ожидаемый вывод и способ проверить ошибку; контракты не требуют догадок.

## Этап 1. PCAP-источник

Зависимость: T03. Это ближайшая задача по коду.

- [ ] T06. Реализовать CapturedPacket и PcapFileSource: владение байтами,
  исходная и захваченная длина, временная метка, тип канального уровня.
- [ ] T07. Читать глобальный заголовок и записи классического PCAP.
  Поддерживаемые порядок байтов и точность времени указать явно;
  неподдерживаемые варианты и PCAPNG отклонять понятной ошибкой.
- [ ] T08. Различать корректный EOF, обрезанный заголовок, обрезанное содержимое
  и недопустимую длину; ограничить размер выделяемого буфера.
- [ ] T09. Заменить фиктивный тест проверками реальных байтов и времён.
  Подключить реализацию в CMake и обеспечить наличие Catch2 в Linux-сборке.
- [ ] T10. Добавить минимальный CLI для чтения PCAP с итоговыми счётчиками
  пакетов, байтов и ошибок.

Готово: небольшой PCAP воспроизводимо читается на macOS и Linux,
повреждённые файлы не принимаются как корректные.

## Этап 2. Заголовки и двунаправленные потоки

Зависимости: этап 1, T03–T04.

- [ ] T11. Реализовать безопасный разбор Ethernet/IPv4/TCP/UDP с проверкой
  длины заголовков, IPv4 options и TCP data offset.
- [ ] T12. Явно классифицировать неподдерживаемые кадры, IP-фрагменты
  и повреждённые пакеты; проверить отсутствие чтения за границами.
- [ ] T13. Реализовать симметричный ключ потока и счётчики направлений.
  Разделить канонический ключ и роль инициатора; при захвате с середины
  соединения роль может быть неизвестна.
- [ ] T14. Реализовать тайм-ауты, RST, TCP half-close и повторное использование
  tuple; ограничить число активных потоков и учитывать вытеснение.
- [ ] T15. Выпускать финальный FlowRecord и периодические ревизии активного
  потока. Использовать время PCAP для тайм-аутов офлайн-воспроизведения.
- [ ] T16. Проверить обратный трафик, повторное соединение, первый FIN,
  долгоживущий поток и ограничение памяти.

Готово: эталонный PCAP даёт ожидаемые потоки, направления и счётчики;
повторные снимки не считаются новыми соединениями.

## Этап 3. Выборочный DPI и TLS

Зависимость: этап 2.

- [ ] T17. Создать интерфейс детектора и состояния: нужны данные, протокол
  определён, не поддерживается, данных недостаточно; добавить бюджет анализа.
- [ ] T18. Реализовать ограниченную сборку TCP-данных для handshake:
  сегментация, повторы, перестановки, пропуски и исчерпание буфера.
- [ ] T19. Разобрать TLS-записи и ClientHello через границы сегментов/записей.
  Извлечь доступные SNI, предлагаемый ALPN, версии, шифры и расширения.
- [ ] T20. Выбрать формат TLS-fingerprint, зафиксировать нормализацию
  и проверить на эталонах; не считать редкость отпечатка доказательством C2.
- [ ] T21. Останавливать ненужный глубокий разбор после получения метаданных,
  сохраняя счётчики. Показывать неполный handshake и недоступные поля.
- [ ] T22. Проверить TLS 1.2/1.3, разделённый ClientHello, отсутствие SNI,
  ECH-сценарий, повреждённые длины и предел памяти с санитайзерами.

Готово: метаданные соответствуют эталонам; неполный разбор виден в результате;
зашифрованное содержимое не разбирается как открытые прикладные данные.

## Этап 4. История, правила и маршрутизация

Зависимости: этап 3, T01–T04.

- [ ] T23. Реализовать окна «узел — назначение» независимо от эфемерного порта:
  число соединений, интервалы, разброс, объёмы и направления.
- [ ] T24. Добавить признаки активности долгоживущих потоков и дедупликацию
  снимков; ограничить размер истории.
- [ ] T25. Создать воспроизводимый baseline-детектор периодичности:
  регулярный beaconing, beaconing с jitter и нормальный периодический фон.
- [ ] T26. Реализовать правила политики и решения для каждого детектора:
  нарушение, без ML, запрос ML, недостаточно данных.
- [ ] T27. Сохранять основание маршрутизации и версии правил; изменение
  поведения узла должно допускать новую проверку ранее разрешённого потока.
- [ ] T28. Добавить контрольную выборку пропущенных наблюдений и режим
  направления всех релевантных наблюдений в ML для экспериментов.

Готово: один и тот же набор событий воспроизводимо формирует окна и решения;
пропуск одной проверки не отключает остальные детекторы.

## Этап 5. Сохранение и первый сквозной интерфейс

Зависимости: этапы 2 и 4, T03. Можно выполнять до готовности ML.

- [ ] T29. Подготовить ClickHouse DDL для потоков, окон, событий, результатов
  анализа и предупреждений; определить срок хранения и выбор актуальных ревизий.
- [ ] T30. Реализовать отдельную ограниченную очередь пакетной записи,
  ограниченные повторы и метрики потерь экспорта при недоступной БД.
- [ ] T31. Создать общий сервис событий: источник rule/ml/hybrid, evidence,
  дедупликация, связь с потоком/окном и состояние анализа.
- [ ] T32. Описать и реализовать REST-контракты просмотра потоков, предупреждений
  и состояния сенсора: фильтры, пагинация, ошибки, версии ответов.
- [ ] T33. Реализовать WebSocket-события после сохранения и восстановление
  актуального состояния через REST после переподключения.
- [ ] T34. Создать React/Vite-приложение: обзор, список потоков, карточка
  предупреждения с основаниями и отображение ошибок/задержек сенсора.

Готово: PCAP со сценарием beaconing создаёт предупреждение по правилу,
которое можно открыть в браузере и связать с исходными наблюдениями.

## Этап 6. Асинхронный ML

Зависимости: этап 4, T02–T03. Интеграция результатов зависит от T31.

- [ ] T35. Подготовить offline-датасет теми же преобразованиями, что применяются
  при инференсе; исключить утечку связанных сессий между train/validation/test.
- [ ] T36. Обучить Isolation Forest на проверенном нормальном трафике.
  Для flow/window-схем сохранять отдельные модели, обработку пропусков,
  feature_schema_version и фиксированные параметры воспроизведения.
- [ ] T37. Подобрать порог на validation; сравнить с baseline-правилом
  на легальном фоне, включая AnyDesk. Test не использовать для настройки.
- [ ] T38. Реализовать пакетный HTTP-инференс с проверкой схемы и версии;
  возвращать job_id, ревизию, anomaly_score, threshold и статус.
- [ ] T39. Реализовать C++ dispatcher: ограниченная очередь, отдельный worker,
  deadline, ограниченные повторы и тот же job_id при повторной отправке.
- [ ] T40. Обработать поздние/повторные ответы, остановленный ML и переполнение:

- [ ] T41. Подключить результат к событию и интерфейсу; показать оценку

Готово: неопределённые наблюдения анализируются асинхронно; повторный ответ

## Этап 7. DNS-политика и выбранные VPN

Зависимости: этапы 3–6; набор профилей определяется в T01.

- [ ] T42. Реализовать проверку разрешённых резолверов и детектор поддерживаемых

- [ ] T43. Реализовать признаки известных DoH-сервисов и оценку неопределённых

- [ ] T44. Реализовать выбранный профиль OpenVPN и оформить ограничения,

- [ ] T46. Добавить разрешения по узлам/сегментам и проверки ложных тревог:

Готово: каждый поддерживаемый сценарий имеет воспроизводимый тест,

## Этап 8. Live-захват и нагрузка

Зависимости: этапы 2–3; полный прогон — после этапов 6–7.

- [ ] T48. Реализовать AF_PACKET/PACKET_MMAP/TPACKET_V3 для Linux с фильтром
  входного трафика, пакетной обработкой и счётчиками потерь.
- [ ] T49. Исключить ненужное копирование и выделение памяти в обработчике;
  обеспечить корректное время жизни данных кольцевого буфера.
- [ ] T50. Снять профиль CPU/RAM одного обработчика. При доказанной необходимости
  добавить распределение потоков между владельцами с сохранением направлений.
- [ ] T51. Испытать высокий packet rate, много коротких соединений,
  долгоживущие потоки, handshake-нагрузку и исчерпание лимитов.
- [ ] T52. Проверить деградацию при медленных ML/ClickHouse и переполнении
  каждой очереди; сравнить с режимом без внешнего I/O.

Готово: получены воспроизводимые показатели пропускной способности,
потерь, памяти и задержки. Слово «высокопроизводительный» подкреплено измерениями.

## Этап 9. Исследование и материалы диплома

Зависимости: завершённый сквозной контур и зафиксированный test-набор.

- [ ] T53. Сравнить только правила, ML всех релевантных наблюдений и каскад
  на одной выборке при одинаковом бюджете ресурсов.
- [ ] T54. Измерить Precision/Recall/F1 по сценариям, ложные тревоги на узел-час,
  долю ML-заданий и ошибки наблюдений, которые отсеял маршрутизатор.
- [ ] T55. Провести ablation: потоковые признаки, добавление handshake,
  добавление истории; отдельно сравнить бюджеты выборочного DPI.
- [ ] T56. Сравнить с применимыми возможностями Suricata и ntopng/nDPI;
  для проверки извлечённых метаданных использовать Zeek. Зафиксировать версии,
  конфигурации, доступные функции и ограничения сравнения.
- [ ] T57. Измерить полную задержку обнаружения, включая накопление окна,
  ожидание очереди и запись; отдельно указать p50/p95/p99 времени инференса.
- [ ] T58. Подготовить воспроизводимый запуск стенда, графики, таблицы,
  ограничения результатов и демонстрацию для предзащиты.

Готово: преимущества или отсутствие преимуществ показаны числами.
Сравнение не ограничивается только наблюдениями, дошедшими до ML.

## Ближайшая последовательность

1. T03 и T06–T10: завершить PCAP-источник и заменить тест-заглушку.
2. T11–T16: получить проверяемые двунаправленные потоки.
3. T17–T22: извлечь TLS ClientHello с ограниченным буфером.
4. T23–T28: собрать историю и получить первые решения детекторов.
5. T29–T34: показать предупреждение по правилу от PCAP до браузера.
6. T35–T41: подключить ML и проверить отказы.

T01–T02 и подготовка размеченного трафика начинаются с первого этапа:
без данных откладывается проверка всей идеи. ML и live-захват не являются
условиями для первых тестов парсеров и сквозного интерфейса.

## За пределами обязательного объёма

QUIC, IPv6, произвольные маскирующие транспорты, HTTP-сигнатуры,
DNS-туннелирование, LLM-анализ и автоматическая блокировка не входят
в этот план. Добавление любого из них требует отдельной оценки объёма.
